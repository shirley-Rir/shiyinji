# 当前完成度与实施顺序

## 1. 当前版本结论

Demo V1 已从纯前端雏形进入“可持久化的 Mock 业务闭环”阶段。用户可以提交文本、图片或图文情境，系统通过统一 API 生成结构化情境、读取账号级画像、召回候选、过滤并排序歌曲，随后记录播放和反馈行为。

这一版验证的是程序链路与模块边界，不代表推荐质量已经成立。`MockAIProvider` 仍使用规则理解情境，`MockMusicProvider` 仍使用开放示例音频；下一阶段的核心工作是用真实多模态模型和可合法播放的音乐源替换它们，并通过测试集验证推荐质量。

## 3. 当前仍为 Mock 的边界

| 模块 | 当前实现 | 下一步替换目标 |
| --- | --- | --- |
| `AIProvider` | 关键词规则与图片元数据 | 多模态模型结构化输出、置信度、冲突判断和消歧 |
| `MusicProvider` | 五首演示曲目与开放示例音频 | 用户授权曲库、歌单导入、搜索、可播放校验与完整播放 |
| 用户画像 | 显式偏好和默认场景画像可持久化 | 从播放、跳过、喜欢等事件增量学习 |
| 候选召回 | Mock 曲库全量召回 | 用户歌单、相似歌曲、场景种子和探索池多路召回 |
| 排序权重 | 可解释固定权重 V1 | 基于情境测试集和用户指标进行离线、在线调权 |
| 图片输入 | 文件参与请求，Mock 仅读取文件元数据 | 模型视觉理解；明确留存策略后再决定是否保存原图 |

## 4. 兼容与衔接设计

- `AIProvider` 只输出 `StructuredContext`，不直接决定歌曲，避免模型供应商与曲库耦合。
- `MusicProvider` 负责候选、可播放校验和播放句柄，推荐服务只处理标准曲目特征。
- `Repository` 隔离 D1 细节，迁移到 PostgreSQL 时 API 和推荐服务无需重写。
- 推荐记录保存情境会话、画像版本、模型版本、分数和解释，便于复现与比较算法版本。
- 客户端播放事件带唯一事件 ID，后续弱网重试时可依靠数据库唯一索引去重。
- 方向调整生成新推荐而不覆盖旧结果，保证反馈链和实验数据可追溯。
- 图片默认不落库，只保存必要元数据；未来接入对象存储必须同步增加生命周期与删除策略。

## 5. 下一阶段实施顺序

```mermaid
flowchart LR
    A[已完成<br/>领域、D1、API、Mock Provider] --> B[多模态语义理解]
    B --> C[真实音乐 Provider]
    C --> D[多路候选召回]
    D --> E[画像学习与排序调权]
    E --> F[封闭测试与指标看板]
```

### 阶段 C：大模型语义理解

- 建立 30 到 50 条覆盖旅游、学习、工作和情绪陪伴的情境测试集。
- 要求模型输出固定 JSON Schema，并验证置信度、图文冲突和缺失字段。
- 保留 Mock Provider 作为开发降级和回归测试基线。

### 阶段 D：真实音乐 Provider

- 先验证账号登录、歌单导入、搜索、Track ID 对齐和可播放性。
- 仅在用户拥有合法播放权限时解析完整歌曲，不接入解灰或音源替换能力。
- 保留开放授权音频作为登录失败或曲目不可播放时的降级曲库。

### 阶段 E：推荐质量验证

- 建立用户偏好召回、情境召回、相似歌曲和探索池四路候选。
- 用离线情境集检查 Top 5 相关性、可解释性、多样性和可播放率。
- 用真实事件衡量 Top 1 接受率、30 秒留存、跳过率和方向调整率。

## 6. 下一轮建议范围

下一轮优先完成“大模型语义理解测试集 + RealAIProvider 适配器”，暂不同时改音乐 Provider。这样可以先判断模型是否真正理解用户当下情境，并把输出稳定在现有推荐引擎可消费的结构上；随后再替换真实曲库，能够分别定位语义误差和歌曲召回误差。
